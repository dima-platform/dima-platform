# DIMA · منصة توصيل في تونس

الإصدار الحالي **0.6.0**. استُؤنف العمل بطلب صاحب المشروع بعد نقطة الحفظ، وأُكمل توثيق الكتالوج وعقده. آخر نتيجة اختبار محلية: 44 ناجحًا، 3 متجاوزة. الحالة التالية محفوظة في [RESUME.md](RESUME.md).

بداية تنفيذ فعلية، وليست منصة مكتملة للإطلاق. تصميم أصلي مستمد من صورة الهوية المرفقة، دون نسخ Snoonu. الألوان الأولية: `#008779` و`#FF7B29`، خلفية `#F5F7F2`. صورة الهوية مرجع بصري وليست ملف شعار متجهيًا جاهزًا للنشر.

**منطقة الإطلاق المعتمدة: ولاية نابل، تونس.** فحص العناوين يستخدم مضلّعًا جغرافيًا مرجعيًا للولاية، وليس وعدًا بتغطية تشغيلية فعلية لكل الأحياء. القرار وتفاصيله في [قرارات المشروع](docs/DECISIONS.md).

## ما يعمل الآن

- عناوين محفوظة للعميل بإحداثيات، تعديل وأرشفة وملكية ونسخ، وفحص جغرافي داخل نطاق نابل وربطه بالمتجر. حفظ snapshot عنوان مستقل لكل طلب، وتفاصيل طلب وسجل حالات في الويب ومصادر Flutter. أُزيل قبول العنوان النصي الحر عند إنشاء الطلب عبر HTTP.
- إضافة منتجات من لوحة التاجر باسمي العربية والفرنسية، مع منع تكرار الإنشاء وسجل تدقيق؛ البحث في المتاجر ومنتجاتها والتصفية حسب المطاعم/المقاضي وصفحات تفاصيل متجر. [دليل الكتالوج](docs/CATALOG.md).

- خادم Node.js بوضع ذاكرة دون تبعيات، ووضع PostgreSQL باستخدام `pg`: متاجر ومنتجات، إنشاء الطلب، احتساب السعر، منع تكرار الإرسال، صلاحيات، حالات الطلب وسجل أحداث.
- واجهة ويب محلية للعميل والمتجر والإدارة والمندوب، مع دخول تجريبي لكل دور. المتجر يدير أسعار المنتجات وتوفرها وفتح استقبال الطلبات، إضافة إلى قبول الطلب وتحضيره. الإدارة تتحكم في تفعيل المتاجر ورسومها وسماح المندوبين باستلام توصيلات جديدة، وتعرض آخر 50 تعديلًا.
- كتالوج الذاكرة معزول لكل خادم ويحترم الإغلاق والتعليق والتوفر. الطلبات السابقة تحفظ الأسعار، والواجهات ترسل إجمالي السلة لمطالبة المستخدم بإعادة التأكيد عند تغير السعر.
- مصادر Flutter لتطبيق العميل (اكتشاف وبحث وتفاصيل متجر، عناوين وسلة وتفاصيل طلب) والمندوب (طلبات جاهزة، قبول، استلام، تسليم) تتصل بخادم العرض. دعم اتجاه العربية والفرنسية وأسماء كتالوج باللغتين؛ رسائل بعض الأخطاء ومحتوى بعض بيانات العرض لا تزال تحتاج ترجمة.
- أضيف مستودع PostgreSQL فعلي ومعاملات ذرّية، وقفل إسناد المندوب، وقيد توصيل نشط واحد لكل مندوب، والتحقق من عضوية المتجر وحالة المندوب، وترحيلات مع checksums وبيانات تطوير. **الكود جاهز للتجربة لكنه لم يُختبر على PostgreSQL في هذه البيئة.**
- رمز تحقق تجريبي ظاهر في الواجهة، وجلسات عشوائية وانتهاء وصول وتجديد دوّار وتسجيل خروج وحدود محاولات. أُزيلت رموز الوصول الثابتة من التشغيل العادي. الجلسات في الذاكرة حتى مع PostgreSQL؛ لا يوجد تحقق ملكية هاتف فعلي أو SMS أو مصادقة إنتاجية.
- اختبارات مجال ومعالج HTTP وجلسات؛ لا يوجد تتبع حي أو مزود رسائل أو خرائط أو دفع إلكتروني.

## تشغيل العرض محليًا

يتطلب Node.js 22 أو أحدث. من هذا المجلد:

```sh
node --test services/api/*.test.mjs
node services/api/server.mjs
```

افتح `http://127.0.0.1:3000`. وضع الذاكرة لا يتطلب تثبيت حزم. الخادم يستمع على الجهاز المحلي فقط ويرفض التشغيل عندما تكون `NODE_ENV=production`. الحسابات الوهمية ورمز التحقق الظاهر في الواجهة للتجربة فقط؛ لا تصلح لأي بيانات حقيقية. تُفقد طلبات وضع الذاكرة وجميع جلسات الدخول عند إعادة تشغيل الخادم. روابط مباشرة للعرض: `/merchant` و`/admin` و`/courier`؛ كل دور يحتاج جلسته، واختيار الدور لا يمنح صلاحية حساب آخر.

### تجربة دورة الطلب

1. اختر العميل، اطلب رمزًا تجريبيًا ثم أدخل الرمز الظاهر وأكد الدخول؛ اختر العنوان الوهمي المحفوظ في نابل أو احفظ عنوان اختبار آخر، ثم أضف منتجًا وأكد الطلب.
2. اختر المتجر، وسجّل دخوله التجريبي: قبول ← تحضير ← جاهز.
3. اختر المندوب، وسجّل دخوله التجريبي: قبول الإسناد ← استلام ← تسليم.
4. اختر العميل أو الإدارة وسجّل دخوله لرؤية الحالة. يمكن فتح أدوار مختلفة في تبويبات مستقلة. تغيير الدور في التبويب نفسه يُخرج الحساب السابق.

تفاصيل الحسابات والرموز والجلسات في [دليل المصادقة التجريبية](docs/AUTH.md). لا تُرسل رسائل SMS ولا يُنشأ حساب حقيقي.

### Flutter

Flutter SDK غير موجود في بيئة التسليم؛ لم يُشغّل المحلل أو المحاكي. ملفات Android/iOS الأصلية لم تُولد بعد. بعد تثبيت Flutter stable، نفّذ داخل كل من `apps/customer` و`apps/courier`:

```sh
flutter create --platforms=android,ios .
flutter pub get
flutter analyze
flutter run --dart-define=API_BASE=http://10.0.2.2:3000
```

احتفظ بملفات `lib` و`pubspec.yaml` المرفقة إذا اقترح المولّد استبدالها. العنوان الافتراضي خاص بمحاكي Android؛ استخدم `http://127.0.0.1:3000` لمحاكي iOS. خادم العرض غير متاح للهاتف الحقيقي عبر الشبكة. الوصول من محاكي Android إلى عنوان loopback للمضيف يعتمد على بيئة المحاكي، ويحتاج تحققًا محليًا. اسمح بـHTTP فقط في إعدادات التطوير Android/iOS عند الحاجة، ولا تضع استثناءات HTTP في إصدار النشر. iOS يتطلب macOS وXcode. المندوب يحتاج تحديثًا يدويًا؛ لا يوجد GPS أو عمل في الخلفية.

### PostgreSQL

بعد تثبيت Docker ومدير حزم Node، انسخ `.env.example` إلى `.env`، واستبدل كلمة المرور في المتغيرين معًا. إذا احتوت كلمة المرور رموزًا محجوزة فرمزها داخل `DATABASE_URL`. ثم:

```sh
npm install
docker compose up -d postgres
node --env-file=.env services/api/migrate.mjs --seed
node --env-file=.env services/api/server.mjs
```

يقرأ الخادم `DATABASE_URL` ويستخدم PostgreSQL تلقائيًا. غيابه يختار الذاكرة، لكن وجوده مع فشل الاتصال يوقف التشغيل ولا يعود للذاكرة بصمت. يُظهر `/health` وضع التخزين ويفحص اتصال DB. تكرار أمر الترحيل آمن؛ seed لا يمسح الطلبات ولا يعيد كتابة الأسعار المعدلة. معرفات وضع DB هي UUID مختلفة عن معرفات الذاكرة، والواجهات تقرؤها من الكتالوج.

ترحيلات SQL يديرها الآن أمر `migrate.mjs`، لا Docker init. إذا كنت شغلت نسخة المخطط السابقة يدويًا أو باستخدام Docker، سيكتشف الأمر الجداول غير المتعقبة ويتوقف قبل تعديلها. استخدم قاعدة تطوير جديدة أو راجع baseline يدويًا؛ لا تحذف volume يحوي بيانات مهمة. لا يوجد ملف lock للحزم بعد، لأن تثبيت الحزم مُنع في بيئة التنفيذ.

### اختبارات الشبكة وقاعدة البيانات

الاختبارات الافتراضية تختبر المجال ومعالج HTTP داخل العملية دون sockets. لتشغيل اختبارَي شبكة HTTP في PowerShell على جهاز يسمح باتصال localhost:

```powershell
$env:DIMA_NETWORK_TESTS='1'
node --test services/api/*.test.mjs
```

لاختبار PostgreSQL، أنشئ قاعدة اختبار مستقلة فارغة، وحدد `TEST_DATABASE_URL` ثم شغّل الاختبارات. تنشئ المجموعة schema معزولًا باسم `dima_test_<uuid>` وتتركه للفحص، ولا تمسح جداول التطبيق. تتضمن إنشاءات متزامنة، إسناد مندوبين باتصالين، rollback، المخزون والعضويات. تستخدم المجموعة بيانات وأرقامًا وهمية فقط. لم تُنفّذ هذه المجموعة هنا.

راجع [تقرير التحقق](docs/VERIFICATION.md) و[التغييرات](docs/CHANGELOG.md).

أدوات المتجر والإدارة وعقد تحديثاتها في [دليل التشغيل الإداري](docs/OPERATIONS.md). طبّق أحدث ترحيلات DB قبل تشغيل الإصدار 0.4.0. لا يمثل زر السماح للمندوب تحقق هوية فعليًا.

الإصدار 0.5.0 يحتاج أيضًا الترحيل 004 ثم seed لإضافة منطقة نابل المرجعية وربط متجري التطوير بها وعنوان وهمي. راجع [العناوين ونطاق الإطلاق](docs/DELIVERY.md). تُحفظ الهندسة محليًا ولا يعتمد التشغيل على تنزيل حدود من الإنترنت. لا توجد خرائط حية أو GPS أو متاجر نابل حقيقية مسجلة بعد.

لتشغيل 0.6.0 على DB حدّث جميع الترحيلات حتى **005_catalog.sql** بالأمر نفسه؛ يضيف حفظ تكرار إنشاء المنتج وsnapshot الفرنسي للطلبات الجديدة. تشغيله في الذاكرة لا يحتاج pg.

## هيكل المشروع

```text
apps/customer/        تطبيق Flutter للعملاء
apps/courier/         تطبيق Flutter للمندوبين
packages/dima_mobile/ الهوية ومكونات العرض وعميل API المشترك
web/                  عرض الويب للعميل والمتجر والإدارة
services/api/         HTTP ومنطق الطلب واختباراته
database/             مخطط PostgreSQL
docs/                 العقد والتصميم وخطة المراحل والاختبارات
```

التطبيقات ولوحات الويب تشترك الآن في مشروع عرض واحد؛ فصل حزم merchant/admin وتسجيل الدخول الإنتاجي جزء من المرحلة التالية. أُضيف الدخول التجريبي إلى الويب ومصادر Flutter، لكن Flutter غير مبني بعد. هذا المجلد هو جذر مستودع التسليم، دون أي ربط بخدمة Git خارجية.
